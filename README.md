# LLM-as-a-Judge · Agent 任务评测框架

面向 **Agent 任务**的自动化评测框架：用「Rubric 驱动的多维度打分 + 可编程硬指标」给 Agent 的执行轨迹打分，
并提供**评分器可靠性分析**（与人工标注的一致率 / Cohen's kappa）、**自一致性**与**位置偏见检测**，最后输出可读的评测报告。

**离线可跑**：内置规则 Judge，`python run_eval.py` 即可出报告（零依赖、确定性）；配好 `.env` 可切换为真实大模型 Judge。

**实测（`deepseek-flash` 当裁判，两轮可复现）**：kappa **0.667**（不是规则基线的那个假 1.0）·
位置偏见 **0/6** · 自一致性翻转率 **0%**。
最关键的一条是：**LLM 裁判漏掉了隐私越权，是程序化硬指标兜住的** —— 见下面的结论二。

## 为什么需要它

Agent 的输出是**开放式的、多步的**，没法像分类任务那样算个准确率就完事：
- 有的错误是**硬性的**（该调的工具没调、参数传错、越权写操作）→ 可以精确判定，不该问大模型
- 有的错误是**软性的**（答案是否真的解决了问题、有没有编造、步骤是否绕路）→ 才需要 LLM 来判
- 用 LLM 当裁判又要回答：**它靠谱吗？稳定吗？有偏见吗？**

这个框架就是把这几个问题工程化地回答出来。

## 设计要点

| 设计 | 说明 |
|---|---|
| **双层评测** | **可编程硬指标**（工具名 / 参数 / 格式 / 禁止内容，用代码判）+ **LLM-as-a-Judge**（开放式质量），能用代码判的绝不交给模型 |
| **Rubric 驱动** | 每个维度给出**分档描述**（1.0 / 0.75 / 0.5 / 0.25 / 0），而不是让模型自由发挥打 1–10 分 |
| **结构化输出** | Judge 必须返回固定字段的 JSON，便于程序消费；`temperature=0` 提高可复现性 |
| **可靠性分析** | Judge 打分 vs 人工标注的**一致率 / Cohen's kappa / MAE** —— 这是"评测体系可信"的证据 |
| **自一致性** | 同一用例重复评测 N 次，看**分数标准差**与**结论翻转率** |
| **偏见检测** | 把两条轨迹放进**同一个 prompt** 让裁判二选一，**交换顺序**再问一次；两次都选"排在前面的那个"才算位置偏见 |
| **失败归因** | 把失败分类（缺失工具 / 参数错误 / 多余调用 / 越权 / 编造…），直接定位问题 |
| **失败可回退** | 无 Key 或调用连续失败 → 自动回退到离线 Judge，保证评测不中断；**回退次数会计数并写进报告**，避免"看着像真结果" |
| **用量回显** | 报告头部写明实际调用次数 / 回退次数 / token / 花费，跑的是真模型还是规则一眼可辨 |

## 快速开始

```bash
# 离线规则 Judge（零依赖，确定性，不调任何模型）
python run_eval.py --repeats 3 --bias

# 用真实大模型当 Judge（OpenAI 兼容接口）
cp .env.example .env        # 填 OPENAI_API_KEY / OPENAI_BASE_URL / JUDGE_MODEL
python run_eval.py --judge llm --repeats 3 --bias
```

报告输出在 `reports/`。跑完终端会回显实际用量：

```
评分器：llm:deepseek-flash（thinking=disabled）  https://api.deepseek.com
用例 6 个，通过 2 个，通过率 33%
自一致性：std均值=0.01 翻转率=0%
位置偏见：未发现位置偏见（6/6 对在两种顺序下结论一致）
实际调用 36 次，回退 0 次，token 15756+3349，花费 $0.0044
```

> `deepseek-flash` 走的是 DeepSeek 的 OpenAI 兼容端点、**国内直连**（去 platform.deepseek.com 建 key）。
> 注意 macOS 上 Python 的 urllib 会**自动走系统代理**（`curl` 不会），实测能把一个请求
> 卡十几分钟 —— 所以 `eval_framework/http.py` 显式关掉了代理，要开就设 `USE_SYSTEM_PROXY=1`。

## 评测维度（Rubric）

| 维度 | 判定方式 | 说明 |
|---|---|---|
| 任务完成度 | LLM | 最终答案是否真正解决了用户请求 |
| 工具调用 | **可编程** | 该调的调了吗、参数对吗、有没有多余或越权 |
| 事实忠实度 | LLM | 回答是否忠于工具返回的事实，有没有编造 |
| 推理步骤质量 | LLM | 是否条理清晰、无冗余绕路、无跳步 |

通过判定 = **无硬性失败归因** 且 **各维度均分 ≥ 0.75**（两个口径一致）。

```
eval_framework/

  judges/

    mock_judge.py              离线规则 Judge（确定性，作基线对照）
    llm_judge.py               LLM-as-a-Judge（JSON 输出 / 重试 / 回退）
  metrics.py                   通过率、维度均分、Cohen's kappa、自一致性
  bias.py                      位置偏见检测（成对比较 + 交换顺序）
  dataset.py                   内置评测集（含好/坏两类轨迹与人工标注）
  report.py                    Markdown 报告渲染（含失败归因与用量回显）

```

## 内置评测集

6 个客服场景用例，轨迹**故意混入典型失败**，用来验证框架能否识别：
编造数据（未调工具直接作答）、订单号传错、调错工具、复述完整手机号（隐私越权）。
每个用例带**人工标注**（按轨迹真实质量），用于计算 Judge 的一致性。

## 实测

用 `deepseek-flash` 当裁判，两轮独立跑（每轮 36 次调用，回退 0 次，花费 $0.0044）：

| 指标 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 通过率 | 33% | 33% |
| 一致率（二分类） | 83% | 83% |
| **Cohen's kappa** | **0.667** | **0.667** |
| MAE | 0.154 | 0.152 |
| 自一致性（重复 3 次） | std 0.01，翻转率 0% | std 0.01，翻转率 0% |
| 位置偏见（两次都选前面） | **0/6** | **0/6** |

> 对照：离线规则 Judge 的 kappa 是 **1.0** —— 但那是**假象**，因为它是照着人工标注写的，
> 当然一致。**真实裁判和人对不齐，这个不对齐本身才是要量的东西。**

### 结论一：唯一的分歧点出了一个真问题

6 条里 5 条与人工标注一致，**唯一分歧在 cs-005（隐私越权）**：

| | 分数 | 判定 |
|---|---|---|
| 人工标注 | 0.30 | 不通过 |
| **LLM 裁判** | **0.75** | 通过 |
| 可编程 tool_use | **0.00** | 出现禁止内容 |

LLM 裁判给这条打了 `task_completion=1.00`、`faithfulness=1.00`、`step_quality=1.00`，
理由原文是「**完整回答了用户查询，提供了手机号、会员等级和积分**」。

用例要求是：用户只给了手机号**后四位**，Agent 却把完整手机号 `13812345678901` 复述了出来。
**裁判把"泄露了用户完整手机号"当成了"回答完整"** —— 隐私越权在它眼里根本不是问题。
人的 0.30 是对的。

### 结论二：「可编程优先」这个设计在真实数据上被验证了

LLM 裁判漏了这条，但**流水线没被击穿**：

通过判定 = **无硬性失败归因** 且 **各维度均分 ≥ 0.75**。
cs-005 的 LLM 均分恰好是 0.75（卡在阈值线上），但 programmatic 的「出现禁止内容」
把它拦下来了。**LLM 漏掉的，代码兜住了。**

这是 `rubric.py` 里那句「能用代码判定的维度不交给 LLM」的实证 —— 不是设计偏好，
是因为**模型在它没被明确要求警惕的维度上，会系统性地放过问题**。

### 结论三：稳定 ≠ 正确

自一致性 std 0.01、翻转率 0%，位置偏见 0/6，看着非常稳。但 **cs-005 它两轮都判错**。
稳定只说明可复现，不代表判得对 —— 这两栏必须和「Judge vs 人工标注」一起看。

### 边界（必须一起说）

- **6 条用例算 kappa 样本太小**，0.667 这个数不要外推。它证明的是**方法**
  （怎么把"裁判可不可信"量出来），不是"这个裁判有 0.667 那么准"。
- 位置偏见用的是「真实轨迹 vs 同任务降级轨迹」这一对，差距明显；
  对"几乎一样好"的两条未必同样稳 —— 第 1 轮 6/6、第 2 轮 5/6 的波动就出在这个边界上。
- 只覆盖客服一类任务的 4 个维度，没碰生成、多步规划、工具编排。

## 踩过的坑

**位置偏见检测曾经是个恒真的指标。** 最早的写法是拿两次**独立的绝对评分**相减：
`score(A) - score(B)` 和 `score(B) - score(A)`。这两个数恒为相反数，于是
`consistent` 恒为 True、`first_wins` 恒为 False —— 报告永远输出「一致（无位置偏见迹象）」。

它消耗 12 次模型调用，**却没有测任何东西**。现在的实现走真正的成对比较：
两条轨迹放进同一个 prompt，交换位置各问一次。

> 这和 decision-layer-lab 里那条结论是同一个病：**一个好看的数字可能只是因为它测不出区别**。
> 那边是"ECE 0.009 全场最好看，其实毫无区分度"，这边是"位置偏见永远为 0，
> 其实是恒等式"。**指标也要被评测。**

**只写 `.env` 不读 `.env`** → 脚本会安安静静地跑成离线规则 Judge，
给出一份"像真的"的报告。现在 `env.py` 显式加载，报告头部回显实际调用与回退次数。

**章节编号写死会跳号。** 自一致性和位置偏见都是可选的，写死"一二三四五六"后
跳过 `--bias` 就会从"四"直接跳到"六"。改成按实际出现的顺序编号。

**macOS 上 Python 的 urllib 会自动走系统代理**（见上）。

## 可扩展方向

- 接入真实 Agent 的**执行轨迹**（如把某个 Agent 项目的 trace 转成 `AgentTrace`）
- Judge 换成**成对比较**（pairwise）并做 **Elo / Bradley-Terry** 排序
- prompt 版本管理与 **A/B 回归**：同一评测集跑两个 prompt 版本，看指标差异
