# LLM-as-a-Judge · Agent 任务评测框架

面向 **Agent 任务**的自动化评测框架：用「Rubric 驱动的多维度打分 + 可编程硬指标」给 Agent 的执行轨迹打分，
并提供**评分器可靠性分析**（与人工标注的一致率 / Cohen's kappa）、**自一致性**与**位置偏见检测**，最后输出可读的评测报告。

**离线可跑**：内置规则 Judge，`python run_eval.py` 即可出报告（零依赖、确定性）；配 `OPENAI_API_KEY` 可切换为真实大模型 Judge。

## 为什么需要它

Agent 的输出是**开放式的、多步的**，没法像分类任务那样算个准确率就完事：
- 有的错误是**硬性的**（该调的工具没调、参数传错、越权写操作）→ 可以精确判定，不该问大模型
- 有的错误是**软性的**（答案是否真的解决了问题、有没有编造、步骤是否绕路）→ 才需要 LLM 来判
- 用 LLM 当裁判又要回答：**它靠谱吗？稳定吗？有偏见吗？**

这个框架就是把这几个问题工程化地回答出来。

## 设计要点

| 设计 | 说明 |
|---|---|
| **双层评测** | **可编程硬指标**（工具名 / 参数 / 格式 / 禁止内容，用代码判）+ **LLM-as-a-Judge**（开放式质量），能用代码判的绝不交给模型 |
| **Rubric 驱动** | 每个维度给出**分档描述**（1.0 / 0.75 / 0.5 / 0.25 / 0），而不是让模型自由发挥打 1–10 分 |
| **结构化输出** | Judge 必须返回固定字段的 JSON，便于程序消费；`temperature=0` 提高可复现性 |
| **可靠性分析** | Judge 打分 vs 人工标注的**一致率 / Cohen's kappa / MAE** —— 这是"评测体系可信"的证据 |
| **自一致性** | 同一用例重复评测 N 次，看**分数标准差**与**结论翻转率** |
| **偏见检测** | 成对比较时**交换顺序**再评一次，检查是否只是偏好"排在前面的那个" |
| **失败归因** | 把失败分类（缺失工具 / 参数错误 / 多余调用 / 越权 / 编造…），直接定位问题 |
| **失败可回退** | 无 Key 或调用连续失败 → 自动回退到离线 Judge，保证评测不中断 |

## 快速开始

```bash
# 离线规则 Judge（零依赖，确定性）
python run_eval.py

# 重复评测 3 次，并做位置偏见检测
python run_eval.py --repeats 3 --bias

# 用真实大模型当 Judge（OpenAI 兼容接口）
export OPENAI_API_KEY=sk-xxx
export OPENAI_BASE_URL=https://api.openai.com/v1     # 可选，指向任意兼容端点
export JUDGE_MODEL=gpt-4o-mini                       # 可选
python run_eval.py --judge llm --repeats 3
```

报告输出在 `reports/`。

## 评测维度（Rubric）

| 维度 | 判定方式 | 说明 |
|---|---|---|
| 任务完成度 | LLM | 最终答案是否真正解决了用户请求 |
| 工具调用 | **可编程** | 该调的调了吗、参数对吗、有没有多余或越权 |
| 事实忠实度 | LLM | 回答是否忠于工具返回的事实，有没有编造 |
| 推理步骤质量 | LLM | 是否条理清晰、无冗余绕路、无跳步 |

通过判定 = **无硬性失败归因** 且 **各维度均分 ≥ 0.75**（两个口径一致）。

## 目录结构

```
run_eval.py                    入口（--judge / --repeats / --bias）
eval_framework/
  rubric.py                    评分维度与分档描述
  programmatic.py              可编程硬指标（工具/参数/禁止内容）
  judges/
    base.py                    Judge 接口
    mock_judge.py              离线规则 Judge（确定性，作基线对照）
    llm_judge.py               LLM-as-a-Judge（JSON 输出 / 重试 / 回退）
  metrics.py                   通过率、维度均分、Cohen's kappa、自一致性
  bias.py                      位置偏见检测（交换顺序比对）
  dataset.py                   内置评测集（含好/坏两类轨迹与人工标注）
  report.py                    Markdown 报告渲染（含失败归因）
reports/                       评测报告输出
```

## 内置评测集

6 个客服场景用例，轨迹**故意混入典型失败**，用来验证框架能否识别：
编造数据（未调工具直接作答）、订单号传错、调错工具、复述完整手机号（隐私越权）。
每个用例带**人工标注**（按轨迹真实质量），用于计算 Judge 的一致性。

## 实测

```
用例 6 个，通过 2 个，通过率 33%
失败归因：缺失关键工具调用 ×2 / 工具参数错误 ×1 / 出现禁止内容 ×1 / 多余工具调用 ×1
评分器可靠性：一致率 100% · Cohen's kappa 1.0 · MAE 0.179
自一致性：重复 3 次，分数标准差 0.0，结论翻转率 0%
```

> 注：离线 Judge 是**规则实现**，与按轨迹质量标注的 ground truth 天然一致（kappa=1.0）。
> 换成真实大模型 Judge（`--judge llm`）后会出现分歧——这正是**可靠性分析**要量化的东西。

## 可扩展方向

- 接入真实 Agent 的**执行轨迹**（如把某个 Agent 项目的 trace 转成 `AgentTrace`）
- Judge 换成**成对比较**（pairwise）并做 **Elo / Bradley-Terry** 排序
- prompt 版本管理与 **A/B 回归**：同一评测集跑两个 prompt 版本，看指标差异
